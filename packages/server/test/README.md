# Custom reaction checks

Run from the repository root:

```sh
npm ci --ignore-scripts --force
node --test packages/server/test/*.test.cjs
node_modules/.bin/tsc --noEmit -p packages/server/tsconfig.json
```

Use Node 20 and npm 10. The upstream manifest's `devEngines` shape is rejected by newer npm; on Linux, `--force` permits installing the locked macOS-only packages for static checks. Installation scripts are disabled. The tests transpile actual server modules using the existing TypeScript dependency and replace external/native boundaries. They never open Messages, send messages, inject helpers or start Electron. The checks workflow runs on `main`, `feature/custom-reactions`, `feature/native-stickers` and pull requests. It also builds the production webpack bundle, without packaging or publishing it.

## Fork production branch

The owner's fork uses `main` as the source base for the custom production deployment. It starts from tested revision `f7045711ef1bf72e8a209b316830db2eef70574c`; the existing `master` history remains unchanged. Both checks and macOS artifact builds run on `main`. Promoting the branch does not activate a deployment or change the installed custom app's identity, paths or updater policy.

The inherited `.github/workflows/main.yml` runs only on pushes to `master` and invokes the upstream publishing configuration. Keep it off `main`. The fork's macOS workflow has read-only repository permissions and uploads CI artifacts only; it does not publish tags or GitHub releases.

## API contract

Received reactions keep `associatedMessageType`: the six classic names, `emoji` / `-emoji` for database codes 2006 / 3006, `sticker` for 1000, and strings for unknown numeric codes. `associatedMessageEmoji` is a separate nullable field, available on macOS Sequoia and newer. It survives history, sockets and reduced notification serialization. Sticker attachments retain `isSticker` in reduced notifications too. Older macOS versions do not select the Sequoia database column. A Sequoia installation with an anomalously old Messages schema still requires native validation; there is no schema mutation or migration.

Send through the existing reaction endpoint with a classic descriptor or one emoji grapheme in `reaction` (for example `"👩🏾‍💻"`); prefix `-` to remove that exact emoji. Socket clients use the existing `tapback` field with the same values. The server validates emoji structure and a nonnegative integer `partIndex`, then sends `reactionType: "emoji"` / `"-emoji"` plus `reactionEmoji` to the helper. Arbitrary text, numeric codes and multiple emojis are rejected.

`server/info` exposes `privateApiCapabilities.customEmojiReactions`, which is true only while the connected `com.apple.MobileSMS` helper explicitly advertises that capability. Missing capability, old helper, another process or disconnect means false. Emoji sends go only to that helper. Received metadata remains available independently. Sticker sending uses the separate experimental capabilities described below.

Custom confirmation checks the sender, target GUID, part, type, emoji, chat and send time. `bp:GUID` is accepted only for part zero for rich-link bubbles. Outgoing promise matching uses metadata, without relying on localized reaction text. A native dispatch without a matching message is an error; there is no automatic retry. Offline checks cannot establish macOS selector behavior, delivery acceptance, replacement/removal persistence or sticker-placement behavior. Those require a controlled native test after review.

## Experimental stickers

The `feature/native-stickers` branch adds authenticated multipart `POST /api/v1/message/send-sticker`: one `attachment`, `chatGuid`, required `tempGuid`, safe basename `name` (at most 255 UTF-16 units), and optional nonempty `stickerLabel` (at most 150 UTF-16 units). It rejects every additional field, including reply targets, placement, reaction and audio fields. The chat must already exist and use iMessage. Each of `privateApiCapabilities.stickerSending`, `stickerRows`, `stickerPlacement` and `stickerReactions` requires its own explicit true from the connected Messages helper. The production helper does not enable these experimental capabilities.

For a row, authenticated multipart `POST /api/v1/message/send-sticker-row` accepts only `chatGuid`, `tempGuid`, and `stickers`, a JSON array of 2 to 10 ordered `{name, stickerLabel?}` descriptors. Files must be named `attachment0` through `attachmentN-1`, with exactly one file per index. Each file retains the standalone limits; the row parser bounds aggregate uploads to 5 MiB and text fields to 8 KiB. The server validates and stages every source before one helper `send-sticker-row` request. There are no individual sends or fallback messages. The helper returns the constructed message GUID and ordered `attachmentGuids`, which the existing transaction data retains.

Authenticated multipart `POST /api/v1/message/send-sticker-placement` accepts one `attachment` and only `chatGuid`, `tempGuid`, `name`, optional `stickerLabel`, `selectedMessageGuid`, required `partIndex`, and a `placement` JSON object. Its five required numeric fields are `x` and `y` in [-4, 4], `scale` in [0.01, 4], `rotation` in [-2π, 2π] radians, and `parentWidth` in [1, 4096] points. These are application input limits, not a claim about Apple's schema or verified remote rendering. The server checks exact target chat and available part-count/run metadata; the helper resolves the actual native target part before dispatch. The returned message must confirm association type 1000, the exact target/part, account ownership, send state and one linked sticker attachment.

Authenticated multipart `POST /api/v1/message/send-sticker-tapback` has the same single-upload fields but rejects `placement`. Add and replacement use this endpoint. Authenticated `POST /api/v1/message/remove-sticker-tapback` accepts only JSON fields `chatGuid`, `tempGuid`, `selectedMessageGuid`, `partIndex` and `reactionGuid`, with no upload or caller transfer identifier. Removal requires the exact owned type-2007 sticker reaction on that target part, then the helper compares its GUID to the current visible native reaction immediately before removal. A newer replacement causes rejection rather than deletion. Add/replacement and removal confirm the exact helper-returned message as type 2007 and 3007 respectively. This experimental native tapback protocol is separate from iPad's observed type-1000 reaction-layout stickers; neither endpoint removes or reclassifies those independent messages. Native send acceptance remains unverified.

The route limits multipart file bytes to 500 KiB before staging, preserves repeated file fields for rejection, bounds text fields to 8 KiB and cleans parsed uploads even when downstream auth or capability checks fail. Header checks accept PNG/APNG, GIF and JPEG with dimensions at most 618 by 618, at most 100 frames and at most 25 million canvas pixels across frames. These checks do not decode pixels; the opt-in native helper must fully decode and enforce the same bounds before dispatch. Neither layer substitutes an ordinary photo send.

The server dispatches native sticker requests only to the capable Messages helper and confirms the exact returned GUID against a fresh, sent, error-free iMessage row from the account owner in the requested chat. Confirmation requires the expected number of unique linked sticker attachments with nonempty sticker metadata. Attachment transfer direction does not establish message authorship. A row's returned transfer GUIDs must match its linked attachments; when the attributed body is available, it must contain only the ordered attachment placeholders with matching GUIDs, part 0, emoji-image markers and requested filenames. Duplicate filenames cannot substitute for the GUID order. A helper response without that row is an uncertain outcome. The server does not retry it. Attempted temporary GUIDs stay blocked for the life of the server process, including successful and uncertain outcomes. The bounded guard refuses additional attempts at 4096 entries without evicting earlier entries. Restart clears this process-local guard; review the chat and reconcile uncertain attempts before restarting or choosing a new temporary GUID. This is not durable exactly-once delivery. Confirmed sends remove unused server-prepared originals while retaining files referenced by the native attachment. Uncertain sends retain their staged files.

Receive serialization always includes allowlisted `metadata.sticker`, including reduced notifications and requests without `loadMetadata`. It decodes only the sticker and attribution binary plists, using pinned `bplist-parser` 0.3.2 with a 64 KiB blob bound, a preparse reference-graph depth/node/cycle check, and bounded primitive values. It exports source bundle ID, pack ID, asset ID, hash, pack name, app-store ID, accessibility label, dimensions and selected size-class fields when present. `pid` is a pack ID; `sbid` or attribution `bundle-id` supplies the source bundle identifier. Placement geometry stays under its allowlisted native keys, preserving finite numeric strings or numbers and omitting missing fields. Coordinate units remain unverified. Effect IDs are preserved without applying unsupported effects. Opaque blobs and unrelated fields never enter this metadata.

Pure inline sticker rows expose `stickerLayout: {attachmentGuids, partIndex: 0}` and each attachment's `metadata.sticker.row: {index, partIndex: 0, count}`. The layout requires a complete attributed body of ordered U+FFFC placeholders, one transfer per run, unique linked sticker attachments, and all runs in part 0 with emoji-image markers. Text mixed with stickers and multiple body objects do not acquire a row classification. Legacy association type 1000 remains `sticker` for independent placements, including reaction-layout stickers with `metadata.sticker.placement.sir: true`; 2007 and 3007 become `sticker-reaction` and `-sticker-reaction`, distinct from those messages and emoji reactions.

Sticker serialization and downloads preserve original bytes even when ordinary image-conversion or resize options are requested. This includes received HEIC artwork; the ordinary JPEG path would lose transparency or animation. Authenticated `GET /api/v1/attachment/:guid/sticker-preview` resolves only that sticker attachment, accepts the existing password/token authentication parameters, and rejects caller paths, resizing and other options. It serves `image/png` for PNG or APNG with bounded size/frame/dimension/alpha headers. Missing or nonsticker assets return 404, oversize input returns 400, unsupported or invalid conversion returns 422, unavailable/busy conversion returns 503, and timeout returns 504. Error bodies contain fixed codes, never native stderr or paths. The original download endpoint remains separate and unchanged.

The preview service snapshots at most 5 MiB into an owner-only job directory and invokes the bundled `appResources/macos/sticker-preview` executable with `execFile`, two path arguments, a ten-second SIGKILL timeout and 8 KiB stdout/stderr bounds. It never compiles at request time or starts a persistent process. The native converter bounds 618-pixel dimensions, 100 frames, 25 million aggregate decoded pixels and 16 MiB encoded output. APNG requires complete frame timing/loop metadata and native roundtrip checks; unknown animation or auxiliary/effect data fails explicitly. Effect metadata must be absent or the exact `-1` sentinel written by `BBHStickerStamp` from the pinned [imsg source](https://github.com/openclaw/imsg/tree/640f58f4f80220b10082eafe4d725049fe2acb77/Sources/IMsgHelper). Other effect values, including 0, remain unsupported rather than inferred to mean no effect. The TypeScript preflight checks protocol fields, PNG/APNG structure, output bounds and hashes; full pixel/alpha/timing verification belongs to the native converter and macOS tests.

The process coalesces matching source requests, runs at most two converter processes and admits at most eight distinct pending jobs. Its private managed cache retains at most 64 image/manifest pairs and 128 MiB, with a 24-hour expiry and source-byte/converter-byte digest keys. Incomplete or corrupt pairs never count as successful previews. Successful and failed jobs remove only their known source, output, manifest and native partial filenames. Later requests prune stale owned jobs; unknown files are preserved. These previews never substitute JPEGs, flatten unknown animation, or overwrite original artwork. [Apple's ImageIO destination API](https://developer.apple.com/documentation/imageio/cgimagedestination) supports explicit image destinations; [Electron's native-image documentation](https://github.com/electron/electron/blob/main/docs/api/native-image.md) guarantees PNG and JPEG across platforms, which does not establish faithful HEIC decoding.

Synthetic checks use the installed multipart parser, generic binary-plist and image-header fixtures, and mocked native/database boundaries. They verify bounds, repeated-file rejection, cleanup, capabilities, one-message row preparation, exact confirmation, concurrent duplicate suppression, receive metadata and ordinary send-route collisions. They do not establish native ABI behavior, remote delivery, placement transforms, row delivery or outgoing sticker tapbacks. Controlled macOS fixtures and native acceptance remain required.

## Separate macOS preview artifact

The preview workflow runs only on the owner's fork, on `main` and `feature/custom-reactions` or by manual dispatch. It builds on an ARM64 `macos-15` runner with Node 20.11, Python 3.11 and the unchanged dependency lock. Package scripts are disabled during installation; the workflow explicitly downloads Electron 25.9.8 and rebuilds the three native modules for that Electron ABI. It tests and embeds helper revision `0a9072f1172bc46f1a33a2bc58b8df05cd8e81ef`, builds the existing UI, then packages a new `BlueBubbles Preview.app` with bundle ID `com.mishdivy.bluebubbles-preview` and version `1.9.9-preview.<server revision>`.

The builder generates the new ASAR integrity record and signs the new app ad hoc. The verified helper retains its build signature and bytes. The build verifies the full app signature, ASAR header integrity and embedded helper hash before creating a ZIP, checksums and a manifest with source revisions, code hashes and workflow provenance. These are CI artifacts, not a published release. The build does not copy, modify or re-sign the installed vendor app. An ad-hoc signature is not Developer ID signing or notarization; installation and privacy permissions remain separate host checks.

For a native-sticker candidate, manually dispatch the same workflow from the
reviewed feature revision with `native_stickers=true`. The explicit
`native-stickers` build profile pins helper
`77227e5bbff6076b3f83a1887fe0092e705bd703`, runs its synthetic tests, and builds with
`BBH_EXPERIMENTAL_STICKERS=1` into its separate output directory. It also tests
and builds the bounded ImageIO converter at build time. Packaging signs that new
executable ad hoc, retains its signed bytes, and verifies its embedded hash. The
manifest records `buildProfile`, `experimentalStickers`, and
`stickerPreviewSha256` alongside the helper and server identities. No compilation
occurs at startup or when someone requests a preview.

Push-triggered builds and manual dispatches without that opt-in keep the stable
helper pin and omit the converter, even if a previous build left a generated
binary in `appResources`. A feature artifact does not grant deployment permission
or establish native send/receive acceptance. Keep the running custom app and its
state until a reviewed update and rollback procedure is approved.

The packaging bootstrap requires an existing owner-only state clone at `~/Library/Application Support/divy-mac-utils/services/bluebubbles-preview/data`, including `config.db`. It chooses that directory before loading any server code. Deployment tooling in `divy-mac-utils` prepares the clone and coordinates the one existing LaunchAgent; this build script never activates an app or switches a process. Preview logs use `~/Library/Logs/divy-mac-utils/bluebubbles-preview/main.log`. Both automatic and manual updater checks and the install endpoint are disabled for the preview. Production app state, logs and updater behavior keep their existing paths and behavior.
